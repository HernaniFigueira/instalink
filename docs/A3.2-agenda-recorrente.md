## Modelo escolhido

Não há um novo tipo de atendimento nem tabela paralela de agenda. Cada ocorrência passa por `createBookingTx` e é um **Booking normal**, com ID, status, cliente, profissional, histórico e eventos próprios.

Campos opcionais/aditivos em `Booking`:

| Campo | Finalidade |
|---|---|
| `seriesId` | UUID gerado pelo servidor, comum às ocorrências |
| `seriesIndex` | Posição original, iniciando em 1 |
| `seriesCount` | Quantidade original de ocorrências |
| `seriesRequestId` | Chave idempotente enviada pelo formulário, isolada por negócio |
| `seriesFingerprint` | SHA-256 do payload relevante; impede reutilizar a chave para uma série diferente |

Nenhuma migração destrutiva: registros antigos continuam sem os campos opcionais. As regras recorrentes não são executadas por cron: as datas são expandidas e todos os Bookings são criados na confirmação. Não há editor de regra ou movimentação coletiva por reagendamento.

Reagendamento de um Booking aberto move somente aquele registro. Quando o fluxo existente recria um atendimento terminal, o novo Booking preserva `seriesId`, índice, quantidade e vínculo `previousId`; o original permanece no histórico. Por isso a quantidade **original** da série não representa a quantidade de versões históricas após recriações.

## UX

O fluxo normal continua cliente → serviço → profissional → data → horário → salvar. Depois de data/horário há apenas a caixa **Repetir este agendamento**, inicialmente desmarcada.

Ao marcar:

- Sem repetição (fecha a configuração);
- Toda semana;
- A cada 2 semanas;
- Todo mês;
- Datas personalizadas.

Automáticas terminam por quantidade (incluindo a primeira ocorrência) **ou** data final inclusiva. Limite explícito: **2 a 366 atendimentos por série**. Não há truncamento silencioso.

Mensal mantém o dia âncora e limita somente meses menores: **31/01 → 28 ou 29/02 → 31/03**. O mês seguinte não herda o dia reduzido de fevereiro.

Datas personalizadas e a lista gerada permitem adicionar/remover ocorrências, alterar data, horário e profissional elegível. Mudanças invalidam a prévia; o usuário valida novamente antes de confirmar. `service.professionalIds` continua sendo a autoridade de elegibilidade no servidor, junto com o escopo do usuário autenticado.

A lista mostra total, numeração, data, hora, profissional e resultado por ocorrência: Disponível, Conflito, Profissional indisponível, Dia fechado (ou erro explícito de data/horário/limite). A confirmação de sucesso exibe as ocorrências efetivamente gravadas, inclusive as datas corrigidas, sem reutilizar cegamente o primeiro dia do formulário.

## API e horizontes

| Operação | Autoridade | Horizonte |
|---|---|---|
| `GET /api/bookings` (slots/dias público) | público | `BookingConfig.horizonDays` |
| `GET /api/bookings?mode=slots-admin` | `requireBusiness(req, businessId, 'agenda')` | 5 anos |
| `POST /api/bookings` sem `asOwner: true` | consumidor/guest | público, mesmo com sessão de lojista |
| `POST /api/bookings` com `asOwner: true` | sessão real + permissão Agenda | 5 anos |
| `PATCH /api/bookings` / reagendamento | sessão real + permissão Agenda + escopo | 5 anos |

`horizonDays` não foi ampliado/migrado: permanece janela pública, default 60 e máximo 365 dias. Dia 60 é inclusivo; dia 61 não oferece slot e não aceita POST quando configurado 60.

`ADMIN_BOOKING_HORIZON_YEARS = 5`, limite inclusivo por calendário, não cinco vezes 365. Em 29/02, o aniversário em ano não bissexto usa 28/02. Datas passadas e horários já passados hoje continuam bloqueados, usando **Business.businessTimezone**. Duração, intervalo, antecedência, disponibilidade, exceções e elegibilidade continuam no motor existente.

Slots administrativos usados por NewBookingSheet, reagendamento, drag e fluxo de agendamento do funil. Acrescentar apenas a query string não concede autoridade. Token Customer não autentica como equipe. Um profissional scoped não pode consultar/criar para outro profissional; sem escolha, a consulta/criação fica no próprio profissional.

### Série: contrato aditivo do POST existente

```json
{
  "businessId": "negocio",
  "asOwner": true,
  "serviceId": "servico",
  "contactId": "contato-existente",
  "date": "2026-09-25",
  "time": "14:00",
  "series": {
    "requestId": "uuid-estavel-do-formulario",
    "occurrences": [
      { "date": "2026-09-25", "time": "14:00", "professionalId": "orlando" },
      { "date": "2026-10-09", "time": "15:00", "professionalId": "orlando" }
    ]
  },
  "preview": true
}
```

O contrato de identidade normal (contato escolhido ou nome/telefone) é reutilizado. `preview: true` valida sem gravar; omitir/usar `false` confirma. O servidor recebe datas explícitas, não confia em cálculos de disponibilidade do navegador.

## Conflitos, atomicidade e idempotência

1. A prévia chama `computeSlots` para cada ocorrência, incluindo ocupação simulada das ocorrências anteriores da própria lista. Não cria contatos, bookings nem eventos.
2. A confirmação revalida a lista inteira sobre o documento fresco, **dentro de `updateDB`**.
3. Qualquer conflito retorna **409 com `occurrences`**, índice, data, hora e motivo. Nenhum Booking da série é persistido. A UI mantém a lista editável para corrigir e confirmar novamente.
4. Todas as ocorrências disponíveis passam pelo `createBookingTx` oficial na mesma transação.
5. Duas submissões com a mesma chave/payload devolvem a mesma série (`replayed: true` no retry); chave repetida com payload diferente retorna 409. Chaves distintas disputando o mesmo slot não criam reserva dupla.

### Garantia entre instâncias

O armazenamento atual é um documento JSONB único. O antigo mutex de `updateDB` protegia apenas uma instância. No Postgres, agora usamos uma conexão e **BEGIN → SELECT ... FOR UPDATE → callback → UPDATE → COMMIT**, com rollback em erro e liberação da conexão. O ajuste é no ponto comum de escrita: deixar outras escritas como last-wins poderia sobrescrever a série mesmo que a criação dela usasse CAS.

O consumidor CAS existente continua compatível (UPDATE condicional disputa a mesma linha). O modo arquivo conserva o mutex para desenvolvimento **em um único processo**; não é uma solução de banco compartilhado entre réplicas. Produção multi-instância deve usar Postgres. O bloqueio tem a granularidade do documento já existente, portanto serializa escritas — não foi introduzida arquitetura nova de filas/locks externos.

## Operação, Cliente 360 e automações

- Cada ocorrência pode ser confirmada, concluída, marcada como falta, cancelada e reagendada individualmente.
- Detalhe exibe vínculo discreto e ação **Cancelar ocorrências futuras da série**, com confirmação explícita.
- `PATCH { businessId, id, action: 'cancel-series-future' }` cancela apenas futuros `pending`/`confirmed`, pelo horário do Business, usando `applyBookingStatusTx`. Preserva passados e terminais. Cancelamento scoped de série mista é recusado, sem cancelamento parcial silencioso.
- Cliente 360 encontra as ocorrências pela identidade canônica existente, com indicação “Série · 3 de 12”. Não cria segunda pessoa, Customer, acesso ou Lead automaticamente.
- `createBookingTx` mantém eventos de criação, CRM e automações existentes por Booking. Cancelamentos usam a máquina oficial de status. Nenhuma automação nova foi criada.
- Testes A3.1 continuam passando; não foram alterados seus testes ou fluxos de cadastro/acesso/Lead.
