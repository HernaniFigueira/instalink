**Contrato batch:** `GET /api/bookings?mode=slots-admin&businessId=...&serviceId=...&gestureBookingId=...&internalSnap=5&dates=YYYY-MM-DD,...` exige sessão + permissão Agenda, Booking acessível no mesmo tenant/serviço e máximo **7** datas ISO válidas/distintas. O `professionalScope` restringe a consulta; duração vem do Booking, sem input arbitrário. O parâmetro público `internalSnap=5` continua inoperante. Retorna `{ days: { [iso]: { slots, byPro, eligibleProfessionalIds, closed } } }`; cada resultado calculado sobre a **mesma instância `guard.db`**, excluindo só o Booking em gesto. Testes comparam os sete resultados (inclusive `byPro`) contra o motor individual e verificam 8+/inválida/repetida → 400 e tenant/escopo/serviço/público recusados. O GET é só preview; PATCH revalida tudo de novo na transação.

**Contagem honesta de `readDB`:** a inspeção do fluxo `requireBusiness` mostra **duas** leituras do documento **por requisição autenticada** (uma em `getUserBySession` e outra dentro de `requireBusiness`); a montagem do batch NÃO chama `readDB` por dia. Assim, na arquitetura atual, as sete requisições anteriores podiam causar até **14 leituras** só no guard; agora é **uma requisição com duas leituras** de autenticação/guard, e sete cálculos puros em `guard.db`. São contagens derivadas do código e requests medidos, **não** uma estimativa de MB nem instrumentação de produção. Reduzir também a leitura duplicada do guard global exige mudança transversal e não foi misturado nesta etapa.

**Atualização local:** resposta PATCH de move/resize ecoa só os campos temporais/operacionais do Booking autorizado (`id`, `date/time`, janela, snapshot, fuso/origem, profissional/status, check-in, histórico, workflow e `updatedAt`) mais `queueChanged`. `applyBookingTemporalPatch` troca somente o registro já existente do mesmo ID/tenant; remove-o quando sai da faixa carregada. `bookingsRef` e detalhe acompanham `setBookings` normalmente. Sem estado otimista antes do 200. Quando um servidor anterior não enviar o eco, o fallback é **um GET de bookings**, nunca `load()` global. Se o move afetou a fila, busca-se apenas `/api/queue`. `apiRequest` evita o evento global de overview nesses dois gestos; a criação continua com o fluxo anterior. Foco/revalidate existente permanece, sem polling novo.
